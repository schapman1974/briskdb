# Generated keys

Status: experimental; shared SQL, durable DDL, Engine, prepared, and HTTP
integration implemented for issue #130

BriskDB can allocate one integer key for a single-row `INSERT` into a
catalog-declared generated-ID table. Allocation is part of the same reconciled
physical operation that writes the row. Adapters consume the key returned by
that operation; they must not query pooled connection state such as
`last_insert_rowid()` afterward.

This contract has three separate parts:

1. the SQL frontend recognizes a finite generated-key declaration and retains
   its logical intent;
2. authoritative catalog provisioning durably activates a versioned policy for
   an otherwise compatible physical table on every shard; and
3. an omitted-key `INSERT` uses that policy to choose an owner, write one row,
   and return its key.

Recognizing or translating DDL is not catalog authority. An omitted-key write
works only after the table catalog declares an active generated-ID policy.

## Accepted DDL

The generated column must use an inline, unnamed `PRIMARY KEY`. The frontend
accepts these source forms; `id` is an example unqualified column identifier,
not a required spelling:

| Source dialect | Accepted declaration | Translation mode | Compatibility output | Policy intent |
| --- | --- | --- | --- | --- |
| SQLite | `id INTEGER PRIMARY KEY AUTOINCREMENT` | `StrictSqlite` or `Compatibility` | `id INTEGER PRIMARY KEY AUTOINCREMENT` | `native_range_v1` |
| MySQL | `id BIGINT PRIMARY KEY AUTO_INCREMENT` | `Compatibility` | `id INTEGER PRIMARY KEY AUTOINCREMENT` | `native_range_v1` |
| PostgreSQL | `id BIGSERIAL PRIMARY KEY` | `Compatibility` | `id INTEGER PRIMARY KEY AUTOINCREMENT` | `native_range_v1` |
| PostgreSQL | `id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY` | `Compatibility` | `id INTEGER PRIMARY KEY AUTOINCREMENT` | `native_range_v1` |

MySQL compatibility mode also accepts
`id BIGINT AUTO_INCREMENT PRIMARY KEY` and canonicalizes it to the same output.
SQLite deliberately requires executable `PRIMARY KEY AUTOINCREMENT` order in
both modes; `INTEGER AUTOINCREMENT PRIMARY KEY` is unsupported. PostgreSQL's
documented forms are the exact order shown above. Canonical compatibility
output always emits `INTEGER PRIMARY KEY AUTOINCREMENT`, while strict SQLite
preserves the accepted normalized source.

Acceptance is structural, not a regular-expression rewrite. The table name is
one unqualified identifier, the generated column is the only generator-like
column in that table, and the generated column has no additional option.
Consequently, forms such as these are unsupported:

- SQLite `INT PRIMARY KEY AUTOINCREMENT`;
- MySQL `INT`, `UNSIGNED`, a missing inline primary key, or an additional
  column option with `AUTO_INCREMENT`;
- PostgreSQL `SERIAL`, `SMALLSERIAL`, `GENERATED ALWAYS`, identity sequence
  options such as `START WITH`, or a table-level primary key; and
- `CREATE TABLE IF NOT EXISTS` for a generated-key declaration.

The normal common-subset restrictions still apply to the rest of the
statement. The pure recognition and translation layer may therefore accept a
supported unnamed literal `DEFAULT` on a non-generated column; the generated
key itself still permits no additional option. That layer does not admit
generated expression columns, triggers, qualified table names, engine clauses,
or caller-authored `RETURNING`.

The durable `Database::apply_generated_table_ddl` boundary is stricter. Its
rollback-only writable-table preflight rejects any physical column default
before publishing a bridge or changing a shard, because SQLite's virtual-table
write callback cannot distinguish an omitted value from an explicit `NULL`.

`TranslatedSql::generated_table_intents()` exposes the zero-based statement
position, decoded table and column identifiers, and
`GeneratedIdPolicyIntent::NativeRangeV1`. `TranslatedSql::source()` retains the
exact logical source, while `sqlite_sql()` holds separate source-preserving
strict SQLite or canonical compatibility output. Compatibility spellings that
produce identical physical DDL do not become the source identity. The
translation step itself is pure and does not run a migration, register a table,
or activate allocation.

## Durable DDL bridge

An initialization owner can consume the supported declaration through one
synchronous database operation:

```rust
let receipt = database.apply_generated_table_ddl(
    SqlDialect::PostgreSql,
    "CREATE TABLE events (id BIGSERIAL PRIMARY KEY, payload TEXT NOT NULL)",
)?;
```

`Database::apply_generated_table_ddl` requires exclusive mutable access before
the `Database` is wrapped in an `Engine`. It accepts exactly one top-level
generated-key `CREATE TABLE`, applies `Compatibility` translation for the
selected SQLite, PostgreSQL, or MySQL dialect, and requires the decoded table
and generated-column names to use BriskDB's canonical lowercase catalog
spelling. It creates the table in the default logical database as `Sharded`,
uses the generated `Int64` column as its shard key, and installs active
`native_range_v1` policy.

The operation currently requires an empty authoritative table catalog and owns
one retained manifest bridge singleton. It is therefore a one-table
initialization API, not an online catalog-editing or multi-table DDL API. An
exact repeat is idempotent. A different dialect, source byte, canonical
physical SQL, or declaration conflicts with the retained request and fails
closed. The physical application schema must also be empty: this operation must
be the original creation path, not an adoption wrapper for a table previously
created with the experimental `/v1/admin/broadcast` endpoint or another schema
migration. That endpoint remains a physical SQLite migration API and does not
invoke this source-dialect bridge.

Offline SQLite import is a separate initialization path. It may explicitly opt
an exact `INTEGER PRIMARY KEY AUTOINCREMENT` Sharded `Int64` table into
`native_range_v1` through the import plan, while never inferring authority from
DDL or `sqlite_sequence`; see [SQLite import](SQLITE_IMPORT.md). An imported
catalog does not retroactively acquire a generated-table DDL bridge.

On success, `GeneratedTableDdlReceipt` returns four durable results:

- `logical_id()`: the version-1 BLAKE3 identity of the exact source dialect,
  exact source bytes, and translation version;
- `physical_migration_id()`: the ordinary schema-migration identity of the
  exact canonical SQLite SQL;
- `provisioning_id()`: the normalized table-policy provisioning identity,
  including the retained provisioning-time physical-schema digest and shard
  count; and
- `table_id()`: the stable authoritative catalog identity published by final
  provisioning.

The logical and physical identities intentionally differ even when several
source dialect declarations translate to identical SQLite DDL. Version 1
freezes the logical-ID byte stream as domain
`briskdb.generated-table-ddl.v1\0`, little-endian digest version `1`, the
little-endian `i64` persisted dialect code, little-endian `u32` translation
version `1`, then the source byte length as a little-endian `u64` and the exact
source bytes.
The physical identity remains the full BLAKE3 digest of the exact canonical
SQLite migration bytes. The provisioning identity retains its separately
versioned declaration-and-schema stream documented in
[the storage-format contract](STORAGE_FORMAT.md).

Manifest version 12 retains the exact source SQL, source dialect, translation
version, canonical physical SQL, enough versioned fields to reconstruct the
derived declaration, all three identities, the provisioning-time schema digest,
lifecycle, and final table ID in `briskdb_generated_table_ddl`. Its lifecycle
is one-way:

1. `ApplyingPhysical` atomically records the logical bridge and begins its
   canonical physical schema-migration row in the same manifest transaction.
2. The ordinary migration journal applies that exact SQLite DDL to each shard
   and commits its ascending durable prefix.
3. `Provisioning` is published only after the physical migration is complete;
   it records the committed physical-schema digest and deterministic
   provisioning identity, installs the matching transient provisioning
   journal, and seeds each active owner's `sqlite_sequence` floor one shard at
   a time.
4. One final manifest transaction publishes the table and active generated-ID
policy, clears the transient provisioning rows, records the stable table ID,
and seals the retained bridge as `Complete`.

Completion keeps the provisioning-time schema digest as historical identity
input. A later supported schema migration may advance the current committed
schema digest without rewriting the bridge or changing the receipt.

Process loss at any durable boundary is restart-safe. Startup first completes
an active physical schema migration, then advances an `ApplyingPhysical` bridge
to provisioning. It reconstructs provisioning only from the retained trusted
declaration, resumes its exact acknowledged shard prefix idempotently, and
publishes `Ready` only after atomic finalization. A complete bridge remains for
audit and exact retry. A bridge/migration/provisioning/catalog mismatch is
corruption rather than permission to infer another request. If a manifest
commit has an ambiguous outcome, close the stale mutable handle and reopen the
data root so startup can recover the durable state.

The exact source SQL is retained permanently and included in the checksummed
manifest. Although the accepted declaration surface is deliberately narrow,
callers should not place sensitive literals in DDL comments or identifiers.

## Insert semantics

Generation is authorized only when all of these conditions hold:

- the target resolves to one authoritative `Sharded` table;
- its generated column is also its visible `Int64` shard key;
- the catalog declares an active compatible generated-ID policy; and
- the generated column is absent from the `INSERT` column list.

The supported generated shape is exactly one nonempty `VALUES` row. For
example, given generated column `id`:

```sql
INSERT INTO events (payload) VALUES (?1)
```

The planner records omitted-key intent without assigning a shard. For
`native_range_v1`, Engine deliberately does not turn that intent into one exact
owner. The lower writable registry maintains an independent round-robin cursor
per table and rotates the start of its active-owner candidate list for each
attempt. It asks Engine for one candidate's bounded pool capacity at a time
using a non-waiting reservation. A busy candidate is skipped instead of queued;
after a candidate is pinned, its `sqlite_sequence` capacity is checked under
that child lock. If its owner range is exhausted, the coordinator releases the
unmutated child and reservation before trying the next active owner.

The first active, immediately admitted, non-exhausted owner receives the row.
The coordinator captures the returned integer on that same handle and reports
the actual physical shard. If the candidate scan completes without a
selection, an observed busy candidate takes precedence as retryable `Busy`;
only when every active owner is proven exhausted is the result
`LimitExceeded`. The rotating start is load distribution, not a promise of
strict shard order when capacity or exhaustion requires fallback. A
caller-supplied HTTP/session `shard_key` is not required and does not
substitute for the missing generated value.

`hilo_v1` retains different admission because its irrevocably consumed ID
determines a hash-routed shard only inside the coordinator. Engine reserves all
possible shard capacities in stable order before the lease is consumed, then
the coordinator writes only the resulting owner. It does not use native's
one-candidate fallback loop.

If `id` appears in the column list, the insert is explicit. This includes an
explicit `NULL`: it never arms allocation. Valid explicit integer IDs retain
their existing validation and owner-aware or legacy hash routing, and their
result contains no generated key. An explicit `NULL` cannot prove a shard key
and is rejected before mutation rather than being silently converted into a
generated insert.

A multi-row `VALUES` insert that omits the generated column is `Unsupported`
and is rejected during planning before pool/coordinator admission, sequence
allocation, or row mutation. BriskDB does not return a partial key list and
does not partially apply the statement. Explicit-key multi-row behavior is
unchanged and remains subject to the existing one-physical-shard write rule.
`INSERT ... SELECT`, `DEFAULT VALUES`, physical defaults, and a caller-authored
`RETURNING` clause are outside this contract.

## Protocol-neutral results

`Engine::execute_write` and `Engine::execute_write_with_context` return
`Routed<WriteResult>`. For one generated row:

- `Routed::shard` is the child that owns the inserted row;
- `WriteResult::rows_affected` is the reconciled physical affected-row count;
  and
- `WriteResult::generated_key` contains the canonical catalog column name and
  a protocol-neutral integer `Value` captured before the physical handle is
  released.

The compatibility methods `Engine::execute` and `Engine::execute_with_context`
continue to return only the affected-row count. They can execute the same
write, but intentionally discard the additive generated-key field.

A generated bound portal returns
`PreparedExecution::GeneratedWrite(WriteResult)` through both routed and
logical portal execution. Explicit-key writes, updates, and deletes retain
`PreparedExecution::AffectedRows`.

## HTTP result

`POST /v1/execute` accepts the same single-row omitted-key SQL without a
`shard_key` when the authoritative policy supplies placement:

```json
{
  "sql": "INSERT INTO events (payload) VALUES (?1)",
  "params": ["created over HTTP"]
}
```

A successful generated insert adds `generated_key` to the established execute
response:

```json
{
  "shard": 2,
  "rows_affected": 1,
  "generated_key": {
    "column": "id",
    "data_type": "int64",
    "value": "4620693217682128897"
  }
}
```

`value` is a decimal JSON string so all 64-bit integers survive clients whose
JSON number implementation cannot represent them exactly. The current native
range policy produces `int64`; the HTTP adapter also renders a future
protocol-neutral `Value::UInt64` as `data_type: "uint64"` plus a decimal
string. Responses for explicit-key writes, updates, and deletes omit
`generated_key` entirely, preserving their existing JSON shape.

The response is returned only after coordinator reconciliation and a known
successful child commit. Cancellation that wins before the commit decision
rolls the child back; once finalization owns that decision, commit wins and the
operation is not reported as cancelled. This does not add a transaction that
spans HTTP requests.

## Feature gates

Omitted-key execution uses the experimental stock-SQLite virtual-table
coordinator and requires both gates:

1. compile BriskDB with Cargo feature `experimental-vtab`; and
2. enable `EngineOptions::with_experimental_vtab_writes(true)`, server flag
   `--experimental-vtab-writes`, or
   `BRISKDB_EXPERIMENTAL_VTAB_WRITES=true`.

Without the Cargo feature, a generated insert is rejected as `Unsupported`.
With the feature compiled but the runtime option disabled, it is rejected as
`FailedPrecondition`. Both failures occur before mutation. DDL recognition and
translation are pure SQL operations and do not require these execution gates.

## Compatibility gaps

`SQLite`, `PostgreSQL`, and `MySQL` in the DDL table identify the selected
source-language parsers; they do not imply completed PostgreSQL or MySQL wire
behavior. The HTTP adapter and protocol-neutral Rust result are implemented
now. PostgreSQL generated-key
type/OID and result behavior remains coordinated with
[issue #33](https://github.com/schapman1974/briskdb/issues/33). MySQL
`AUTO_INCREMENT` result/status encoding remains coordinated with
[issue #44](https://github.com/schapman1974/briskdb/issues/44). There is
currently no MySQL listener, and the PostgreSQL listener still defers SQL
execution.

This release does not promise PostgreSQL sequence objects or sequence options,
MySQL session variables such as `LAST_INSERT_ID()`, caller-authored
`RETURNING`, bulk generated-key lists, gapless IDs, numeric commit order,
cross-shard transactions, or generation on `Global` tables. The generated IDs
are globally unique within their versioned policy namespace, but failures and
restarts may leave gaps as documented by the allocation policy.

`hilo_v1` has a lower allocator and can serve the same single-row omitted-key
engine shape when that policy was explicitly provisioned, but it has no SQL DDL
spelling in this compatibility release. Every accepted declaration in the DDL
table requests `native_range_v1`.
